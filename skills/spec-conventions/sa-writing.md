# SA 寫作指引

以讀者能理解並核對為目標。SA 預設沿用下列 ESP postmail 交付文件結構；使用者或目標專案另有明確格式時優先採用，並說明差異。章節結構與 ESP 專屬配號、技術棧及發布流程分開處理。

## 文章結構（ESP postmail 基準）

以 `ESP-Knowledge/SA/postmail/ESP_PM_0001～0004` 實際 Markdown 對照 `_conventions.md` §4 與 `sa-document-structure.md` v5，採用以下章節、順序及標題層級：

```markdown
# 1. 功能概述
# 2. 作業流程圖
# 3. 功能畫面
## <畫面名稱與導覽路徑>
### 3.1 畫面說明
### 3.2 畫面欄位說明
# 4. 使用案例總覽
## 4.1 使用案例圖(UML)
## 4.2 使用案例清單
# 5. 使用案例
## <UC 編號> <使用案例名稱>
### 5.1 使用案例說明
### 5.2 使用 API 清單
### 5.3 使用 Action 清單
### 5.4 循序圖
### 5.5 ERD
# 6. 補充資訊
```

- §1 用 2～3 句交代誰操作、業務目的、系統處理與結果。§2 畫出入口、正常操作、條件分支、例外與結果。
- §3 是畫面物件清單：依導覽順序，每個主畫面、彈窗、Tab 各一個物件，各自重複 3.1／3.2；共用畫面只寫一次。3.1 嵌入可用截圖並標示實機、AS-IS 或 simulation，無圖時提供精確描述與原因。
- §4.2 表頭為「使用案例／編號／參與者／觸發方式／說明」。§5 依該表順序逐筆建立 UC 物件，各自重複 5.1～5.5，不合併為一組共用細節。編號沿用目標專案；未配號明示待確認，不捏造 ESP 代號。
- 必要子節不適用時保留標題，寫明原因與依據。非 UI 功能在 §3 說明端點使用情境或排程／操作介面，無 HTTP API 時於 5.2 說明實際觸發方式。
- §6 為功能層級單一章節；6.x 按需求安排代碼、訊息、輸出契約、規則、限制及驗證證據，不照抄郵件業務子標題。本次沿用 postmail 結構時保留第 6 章，無補充內容則註明「無」及原因（ESP 原規範將此章列為選用）。
- 文件狀態與驗證限制可放正文前；候選稿、Mock 圖片與人工豁免不代表正式驗收或發布完成。

## 表格與內容分工

§3.2 依畫面內容分表，保留欄位順序：

| 子表 | 欄位 |
|---|---|
| A 查詢條件 | 欄位名稱／說明／前端欄位型別／顯示方式／後端資料型別及長度／範例／必填／編輯／預設值 |
| B 明細表格 | 欄位名稱／說明／UI 型別／顯示方式／後端資料型別／範例 |
| C 小計區（有加總時） | 欄位名稱／說明／UI 型別／顯示方式／後端型別／計算方式 |
| D 按鈕或功能區 | 按鈕或功能名稱／說明／顯示方式／型別／檢核說明 |
| 下拉或選項來源（有選項時） | 下拉或選項欄位／選項值欄位／顯示文字欄位／DB 來源／查詢條件或代碼群組／排序規則／證據位置 |

非 DB 選項寫明常數或實際來源，不以「系統載入」取代來源；沒有相應畫面內容的子表說明不適用，不編造欄位。

- **5.1** 用「項目／說明」表依序列 11 項：UC No.、UC Name、角色、功能概述、事先條件、限制條件、觸發條件、基本流程、替代流程、異常處理、後續處理；沒有 Root UC。基本流程用編號，替代流程用 AF、異常用 EF，寫出觸發、系統回應、回到或終止的步驟。
- **5.2** 逐筆列本 UC 的 API：代號或識別、用途、實際協定及端點／operation、輸入、回傳與錯誤。按已核准或已驗證來源填寫，未知值明示待確認。
- **5.3** 表頭為「#／Action 名稱／Action 步驟／預計 Input／預計 Output／API 代號／備註」。按執行順序對照 5.1 步驟與 5.2 API，以業務語言描述，不塞 SQL；無呼叫時 API 填「無」，循序圖不虛構後端呼叫。
- **5.4** 循序圖涵蓋基本、替代及異常流程，交代前後端、資料庫與外部系統；可用階段橫幅對照 5.1 步驟。
- **5.5** 資料實體關係、欄位說明及資料來源查詢。可引用已核實 SQL；使用動態 ORM／Specification 時說明條件、關聯與來源，不捏造可執行 SQL。

## 寫作與交付核對

正文直接說明業務事實，引用本文件章節或已核實程式位置，不反覆引用內部 analysis／requirements 產物路徑。長規則放 5.1，互動放 5.4，訊息及補充規則放第 6 章，避免在流程圖後與每張表重複全文。

沿用 postmail 的 Azure DevOps Wiki 版面時，Mermaid 使用 `::: mermaid`；目標平台不同則調整包裹語法，保留圖的內容與位置。沿用文章結構不要求複製 ESP 的 CJK 字數閘門、配號區間、網路磁碟發布或開發管線。

交付前核對：章節順序；每畫面僅一組 3.1／3.2；4.2 與 §5 的 UC 一對一；每 UC 齊備 5.1～5.5；表格、Action、圖及契約一致；不適用原因及驗證限制可見。不要使用已淘汰的 4.1～4.7 UC 明細骨架，也不要拆成 Hub 加單 UC 兩層文件。

## 共通原則

- 先確認文件目的、讀者、範圍與可用來源。區分已查證的現況、已核准的目標需求與實作後的事實；不要把現況推定為目標，也不要將尚未驗證的設計寫成已實作。缺少依據或有衝突時標明待確認及來源，不自行編造。
- 業務敘述使用自然、具體的中文和短句，一句表達一件事；沿用使用者熟悉的名稱，必要術語首次出現時解釋。讀者若是技術人員，保留理解與實作所需的精確資訊。
- 對適用的功能，說明觸發條件、操作或處理、結果及重要例外，讓讀者能判斷何時完成。欄位、畫面、介面、資料、權限與非功能需求只在本次適用時描述，並與核准來源一致。
- 表格與圖表只在有助理解時使用；每個欄位或儲存格聚焦其用途，較長的規則放在適當的說明並交叉引用。圖表、文字及相關契約應互相一致；技術名稱、代碼、訊息與契約值維持原貌。
- 交付前依範圍檢查完整性、一致性、可驗證性及來源追溯；說明尚未確認或驗證的部分。是否提供圖表、截圖、SQL、驗收案例及其格式，依需求和專案規範決定。
