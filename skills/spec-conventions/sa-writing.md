# SA 寫作指引

以讀者能理解並核對為目標。先採用使用者或目前專案核准的格式；沒有範本時可參考下列通用結構，按實際功能調整。業務規則、配號、技術棧與發布流程須從目前專案取得，不由全域 skill 預設。

## 文章結構示例

以下章節、順序及標題層級供沒有既有範本時參考；採用此結構後，依下方對照方式保持內部一致：

```markdown
# 1. 功能概述
# 2. 作業流程圖
# 3. 功能畫面
## <畫面名稱與導覽路徑>
### 3.1 畫面說明
### 3.2 畫面欄位說明
# 4. 使用案例總覽
## 4.1 使用案例圖(UML)
## 4.2 使用案例清單
# 5. 使用案例
## <UC 編號> <使用案例名稱>
### 5.1 使用案例說明
### 5.2 使用 API 清單
### 5.3 使用 Action 清單
### 5.4 循序圖
### 5.5 ERD
# 6. 補充資訊
```

- §1 用 2～3 句交代誰操作、業務目的、系統處理與結果。§2 畫出入口、正常操作、條件分支、例外與結果。
- §3 是畫面物件清單：依導覽順序，每個主畫面、彈窗、Tab 各一個物件，各自重複 3.1／3.2；共用畫面只寫一次。3.1 嵌入可用截圖並標示實機、AS-IS 或 simulation，無圖時提供精確描述與原因。
- §4.2 表頭為「使用案例／編號／參與者／觸發方式／說明」。§5 依該表順序逐筆建立 UC 物件，各自重複 5.1～5.5，不合併為一組共用細節。編號沿用目標專案；未配號明示待確認，不捏造專案代號。
- 必要子節不適用時保留標題，寫明原因與依據。非 UI 功能在 §3 說明端點使用情境或排程／操作介面，無 HTTP API 時於 5.2 說明實際觸發方式。
- §6 為功能層級單一章節；6.x 按需求安排代碼、訊息、輸出契約、規則、限制及驗證證據，不照抄其他功能的業務子標題。採用本示例時，無補充內容可註明「無」及原因；是否保留章節依目標範本決定。
- 文件狀態與驗證限制可放正文前；候選稿、Mock 圖片與人工豁免不代表正式驗收或發布完成。

## 表格與內容分工

§3.2 依畫面內容分表，保留欄位順序：

| 子表 | 欄位 |
|---|---|
| A 查詢條件 | 欄位名稱／說明／前端欄位型別／顯示方式／後端資料型別及長度／範例／必填／編輯／預設值 |
| B 明細表格 | 欄位名稱／說明／UI 型別／顯示方式／後端資料型別／範例 |
| C 小計區（有加總時） | 欄位名稱／說明／UI 型別／顯示方式／後端型別／計算方式 |
| D 按鈕或功能區 | 按鈕或功能名稱／說明／顯示方式／型別／檢核說明 |
| 下拉或選項來源（有選項時） | 下拉或選項欄位／選項值欄位／顯示文字欄位／DB 來源／查詢條件或代碼群組／排序規則／證據位置 |

非 DB 選項寫明常數或實際來源，不以「系統載入」取代來源；沒有相應畫面內容的子表說明不適用，不編造欄位。

- **5.1** 用「項目／說明」表依序列 11 項：UC No.、UC Name、角色、功能概述、事先條件、限制條件、觸發條件、基本流程、替代流程、異常處理、後續處理；沒有 Root UC。基本流程用編號，替代流程用 AF、異常用 EF，寫出觸發、系統回應、回到或終止的步驟。
- **5.2** 逐筆列本 UC 的 API：代號或識別、用途、實際協定及端點／operation、輸入、回傳與錯誤。按已核准或已驗證來源填寫，未知值明示待確認。
- **5.3** 表頭為「#／Action 名稱／Action 步驟／預計 Input／預計 Output／API 代號／備註」。按執行順序對照 5.1 步驟與 5.2 API，以業務語言描述，不塞 SQL；無呼叫時 API 填「無」，循序圖不虛構後端呼叫。
- **5.4** 循序圖涵蓋基本、替代及異常流程，交代前後端、資料庫與外部系統；可用階段橫幅對照 5.1 步驟。
- **5.5** 資料實體關係、欄位說明及資料來源查詢。可引用已核實 SQL；使用動態 ORM／Specification 時說明條件、關聯與來源，不捏造可執行 SQL。

## 儲存格可讀性（ELI5）

SA 的業務敘述要讓業務、開發與測試讀者一次看懂；技術契約仍保留精確名稱和值。若使用者指定其他受眾或用途，依其調整。ELI5 是把話說清楚，不是幼兒化或刪減規則。

- 每格只回答該欄的問題。「說明」寫用途，「必填」寫是否必填，「預設值」寫實際值，「檢核說明」寫條件與失敗結果；不要在同格混入實作歷史、SQL、來源清單與全部例外。
- 用「誰＋做什麼＋結果」的短句；條件寫成「若……，則……」。例如把「執行起迄值成對性檢核」寫成「起日和迄日必須一起填寫」。不能把嚴格小於改成小於等於，也不能把「或」改成「且」。
- 同格有獨立規則時用編號短句，Markdown 表格可用 `<br>` 分行；避免用逗號、分號或括號串成一整段。不要只插入換行而留下同樣難懂的長句。
- 需要多步處理、複雜分支或長篇說明時，格內留下可判讀的條件與結果，細節移至本文件的流程、規則或錯誤訊息段落，以精確章節／規則編號連結。移出的內容必須實際存在，不得只寫「詳見相關文件」；也不得為維持短格而刪除例外。
- 用畫面標籤稱呼業務欄位；必要術語首次出現時補一句意思，例如「前端（使用者操作的畫面）」。API、型別、欄位代碼、數字、單位、錯誤碼與訊息原文維持原樣，集中在對應技術欄或訊息表，避免每句重複代碼。
- 字數限制依目標專案，不把 ESP 的 60 個 CJK 字限制變成全域門檻。5.1 的完整流程也要分步寫清楚，不以縮字或移到另一個超長儲存格處理。

以下為虛構的寫法示例，不是新增業務規則：

| 欄位 | 難讀的寫法 | 改寫後 |
|---|---|---|
| 檢核說明 | 查詢期間須具備成對完整性且起值嚴格小於迄值，違反時阻斷後續呼叫。 | 1. 起日和迄日必須一起填寫。<br>2. 起日必須早於迄日。<br>不符合任一條件時，不送出查詢。 |
| 說明 | 回應集合為空時維持既有呈現，不進入檔案產製程序。 | 查無資料時，保留目前畫面，不產生下載檔案。 |

改寫後逐項對照原文的條件、否定詞、數字與單位、責任端、結果、例外、未定案狀態及來源。拆到其他章節的內容也要一起核對；原文有矛盾就標明待確認，不自行改成看似合理的規則。讀者應能從該列及其明確引用回答「何時適用、要做什麼、失敗怎麼辦」。

維護依據：`eli5-conversational` 的精確度保留原則，以及 ESP `_conventions.md` §6.4 的儲存格單一職責、長內容移出與交叉引用規則；僅抽取通用寫法，不沿用其專案字數閘門。此處已自足，Codex／Claude 不必另外安裝 ELI5 skill 才能使用。

## 寫作與交付核對

正文直接說明業務事實，引用本文件章節或已核實程式位置，不反覆引用內部 analysis／requirements 產物路徑。長規則放 5.1，互動放 5.4，訊息及補充規則放第 6 章，避免在流程圖後與每張表重複全文。

Mermaid 包裹語法依目標平台決定，例如 Azure DevOps Wiki 使用 `::: mermaid`。字數限制、配號、發布位置與開發管線依目前專案的明確規範處理。

交付前核對：章節順序；每畫面僅一組 3.1／3.2；4.2 與 §5 的 UC 一對一；每 UC 齊備 5.1～5.5；表格、Action、圖及契約一致；不適用原因及驗證限制可見。是否拆分多份文件及 UC 子節編排依目前專案範本決定，不將其他專案的淘汰或採用決策當作全域限制。

## 共通原則

- 先確認文件目的、讀者、範圍與可用來源。區分已查證的現況、已核准的目標需求與實作後的事實；不要把現況推定為目標，也不要將尚未驗證的設計寫成已實作。缺少依據或有衝突時標明待確認及來源，不自行編造。
- 業務敘述使用自然、具體的中文和短句，一句表達一件事；沿用使用者熟悉的名稱，必要術語首次出現時解釋。讀者若是技術人員，保留理解與實作所需的精確資訊。
- 對適用的功能，說明觸發條件、操作或處理、結果及重要例外，讓讀者能判斷何時完成。欄位、畫面、介面、資料、權限與非功能需求只在本次適用時描述，並與核准來源一致。
- 表格與圖表只在有助理解時使用；每個欄位或儲存格聚焦其用途，較長的規則放在適當的說明並交叉引用。圖表、文字及相關契約應互相一致；技術名稱、代碼、訊息與契約值維持原貌。
- 交付前依範圍檢查完整性、一致性、可驗證性及來源追溯；說明尚未確認或驗證的部分。是否提供圖表、截圖、SQL、驗收案例及其格式，依需求和專案規範決定。
