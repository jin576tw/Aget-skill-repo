# start-work

## 完成目標

交付使用者要求的行為與可核對驗證，保留既有變更及已接受的決策。主會話可直接探索、實作、測試與審查，執行方式依任務契約與技術依賴決定；不在通用規範固定模型、Agent 或單一 AC 回合。

## 判斷與驗收

- 清楚集中的需求直接處理；跨 session、共享依賴或多項交付需要持久協調時，使用 start-plan。已有計畫則接續，不重做 intake 或已完成目標。
- 未知只補足會改變交付的資訊；需求未定義的規則（如比對方式、欄位、錯誤格式）不自行擴充，採不增加行為的解讀並回報待確認。沿用已有授權，不在每個環節重複確認。需不可逆操作、外部發布或決策缺口時依適用授權處理。
- 需求／spec 與實作、測試保持可追溯。適用已核准 SA 時核對順序、欄位、訊息、驗收條件，避免照錯誤 spec 做也判通過。
- 依變更風險驗證實際行為與相關回歸。使用 tdd 時維持 test-first；不為純文件、低風險可逆調整制造無意義測試。
- GUI／CSS 的可見行為須在實際頁面觀察；mock 的證据不能冒充真實後端整合。驗證不可用則記錄具體缺口，仍完成不受影響的工作。
- 自審與獨立審查分開；有獨立性要求時不能用主會話自審冒充。委派或跨 session 時以 [Execution Brief](references/execution-brief.md) 提供目標、scope、不可改行為、Context、AC、驗證與 Done；可引用既有 spec／board，不以角色存在作觸發理由。
- 執行者在授權範圍內完成實作、適用驗證及本次變更造成的失敗修復；回報證據與缺口。控場者核對任務結果、必要整合與 review，子任務完成不代表全案完成。
- 里程碑、暫停及接續使用 handover；全案完成後依其 finalize 契約結案。測試通過本身不等於需求或知識蒸餾完成。
