# Execution Brief：執行任務包

在委派、換 session 或需要縮小執行範圍時使用。控場者將需求轉為足夠執行的契約；集中的主會話工作可直接沿用對話，不另建文件或 board。永久規範保存穩定邊界，任務資訊放在本次 brief、spec 或 locked contract，使用連結避免重複維護。

## 任務資訊

以下是資訊需求，不是固定章節或操作順序；已有 spec／board 涵蓋時直接引用。詳細度依任務未知、風險及執行者需要調整，不只按模型名稱判斷。

| 資訊 | 需要讓執行者知道什麼 |
|---|---|
| Objective | 要解決的問題與可觀察的預期行為 |
| Scope／Non-Goals | 可修改的 repo、檔案或模組；不可改動的行為、介面與範圍 |
| Context | 目前核准 spec／SA、程式入口、相關測試與已接受決策；指向必要位置 |
| Acceptance | 適用 AC、前提、預期結果、邊界與錯誤情境 |
| Tests | 適用驗證層級、已知命令／環境與要觀察的結果；未知標明，不虛構命令 |
| Done／Evidence | 哪些成果與實際證據足以完成此任務，哪些缺口須回報 |

任務可以涵蓋一條 AC 或一組相關 AC，依相依性與可驗證交付拆分。測試案例如何拆分不決定派工批次；需要採 TDD 時，維持真實 test-first 證據。

## 執行與回報邊界

執行者在已授權範圍內實作、執行適用驗證、修復本次變更造成的失敗，再重跑受影響檢查；不能把第一版實作當成完成，也不需逐步重新取得相同授權。無關既有失敗須辨識並回報，不擅自擴張修復範圍。

需求或來源衝突、必要環境不可用、或必須超出 scope 才能繼續時，回報具體缺口並完成不受影響的部分。不得改弱 AC 或斷言來湊通過。

回報包含交付與 AC 的對應、實際修改、驗證命令及結果、證據位置與未完成項目。控場者核對證據、跨任務整合與必要 review；子任務完成不代表全案完成，自審也不冒充獨立審查。角色與模型依本次配置及宿主授權選用，不由此範本固定。
